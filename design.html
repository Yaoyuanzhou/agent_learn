快速开始

第一步：配置 API Key

只需修改 config.py 一个文件，填入你的大模型接口信息：

# config.py —— 改这三行就够了
LLM_BASE_URL = "https://api.deepseek.com/v1"   # 国产模型 OpenAI 兼容接口
LLM_API_KEY  = "sk-你的key"
LLM_MODEL    = "deepseek-chat"                  # 或 qwen-turbo / qwen-plus 等

第二步：安装依赖

# 推荐使用 venv 隔离环境
python3 -m venv .venv
source .venv/bin/activate          # macOS / Linux
.venv\Scripts\activate             # Windows

pip install -r requirements.txt    # 约 800MB（主要是 torch）
⏱ 首次安装说明：
torch 约 800MB，建议使用国内镜像：pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple
sentence-transformers 会在第一次运行 RAG 模块时自动下载 BGE 模型（~100MB），保存在 ~/.cache/huggingface/，后续不再重新下载。

第三步：运行

# ── 激活环境后直接用 ──────────────────────────────────
source .venv/bin/activate

# 单 Agent（ReAct 模式，默认）
python agent.py "北京今天天气怎么样？"
python agent.py "计算 sqrt(256) + sqrt(144)"

# 多 Agent 模式（搜索 + 写作 Pipeline）
python agent.py "向量数据库的核心原理" --mode multi

# RAG 模式（加载本地文档后回答）
python agent.py "这批文档讲了什么？" --mode rag --docs ./data/docs

# 单独学习某个模块
python 01_cot/simple_cot.py           # CoT 对比实验
python 02_react/react_agent.py        # ReAct 主循环
python 02_react/reflexion_agent.py    # 失败→反思→重试

01_cot — 思维链（Chain of Thought）

让模型「先想后答」的最简单技术 · 无需任何框架
核心思想：在 Prompt 中加一句「请一步一步思考」或提供带推理过程的示例， 模型的回答准确率会显著提升——尤其是数学、逻辑、多步骤推理类问题。 这是所有 Agent 技术的思维基础。

文件：01_cot/simple_cot.py

三种模式对比

模式核心做法Prompt 差异适用场景
直接回答 不加任何引导 "直接给出答案，不要解释" 简单事实查询
Zero-Shot CoT 问题末尾加魔法句 "请一步一步思考，最后给出答案" 大部分推理问题，零成本
Few-Shot CoT 提供 2–3 个推理示例 示例格式：问题→思考→答案 需要特定输出格式时

执行流程

1 direct_answer(question) → 直接发给 LLM，不展开推理，得到简短答案
2 zero_shot_cot(question) → 在用户消息末尾拼接「请一步一步思考」，模型自动展开推理
3 few_shot_cot(question) → Prompt 中先写 2 个示例（含推理过程），再跟真实问题
4 __main__ 里并列打印三种结果，直观对比效果差异
学完这里你能理解： Prompt Engineering 的核心是「给模型设计思维脚手架」。 Zero-Shot CoT 是成本最低的提升手段，只需一句话。 模型不是「不会算」，而是在没有推理空间时直接猜答案。

02_react — ReAct + Reflexion

Agent 核心循环：Thought → Action → Observation
核心思想：ReAct = Reasoning + Acting。 模型不再「一步到位」，而是进入一个循环： 先思考（应该做什么），再行动（调工具），再观察（工具返回了什么）， 再继续思考……直到任务完成。 这是现代 AI Agent 的最基础架构。

文件清单

工具集
tools.py
定义三个 Mock 工具：search（网络搜索）、calculator（数学计算）、get_weather（天气查询）。 包含两个关键部分：
TOOL_SCHEMAS：OpenAI Function Calling 格式的 JSON Schema，告诉 LLM「有哪些工具、参数是什么」
execute_tool(name, args)：根据工具名字分发到对应函数并执行
定义 JSON Schema→注册到工具表→execute_tool 路由
核心循环
react_agent.py
run_react(task) 实现 ReAct 主循环。每一步：
1. 把当前对话历史发给 LLM（带工具列表）
2. LLM 要么给出最终答案（结束），要么请求调工具
3. 执行工具，把结果作为「Observation」追加进对话历史
4. 回到第1步，最多循环 MAX_STEPS=10 次
用户任务→LLM决策→有工具调用?→执行→注入Obs→循环/结束
反思变体
reflexion_agent.py
Reflexion = ReAct + 失败后反思。LLM 作为评估器判断回答是否合格， 失败则生成一段「反思文字」（哪里错了、下次怎么改）， 存入 memory 列表，再次尝试时把历史反思注入 Prompt。 最多重试 3 次。
执行任务→LLM评估→FAIL→生成反思→memory.append()→注入重试

ReAct 完整流程图

关键代码理解

# react_agent.py 核心逻辑（简化版）
messages = [system_prompt, user_task]

for step in range(MAX_STEPS):
    response = chat_with_tools(messages, tools=TOOL_SCHEMAS)
    messages.append(response)           # 把LLM回复加入历史

    if not response.tool_calls:
        return response.content           # LLM不调工具了 → 任务结束

    for tool_call in response.tool_calls:
        result = execute_tool(tool_call.name, tool_call.args)
        messages.append({"role": "tool", "content": result})  # Observation注入
「写入记忆」是什么？
reflexion_agent.py 第 46 行：memory: list[str] = []，这就是记忆——一个普通 Python 列表。 每次失败后 memory.append(reflection) 把反思文字追加进去。 下次重试时，把 memory 里的内容拼接到 Prompt 里注入给 LLM。 「写入记忆」没有任何魔法，就是字符串拼接。 更高级的实现可以换成 SQLite、向量库等持久化方案（见 05_memory）。

03_tools — Function Calling 底层机制

理解 LLM 调用工具的底层协议 · 四轮对话完整流程
与 02_react 的关系：02_react 的工具调用是「用起来」，03_tools 是「理解原理」。 这里的代码更底层，直接用 OpenAI client 而不是封装好的 chat_with_tools， 帮你看清楚每一轮消息的格式和对话历史的变化。

文件清单

完整流程
function_calling.py
run_function_calling() 直接调 openai.client.chat.completions.create()， 打印每一轮：发了几条消息、LLM 要求调哪个工具（含参数 JSON）、工具返回什么、最终答案。 适合彻底搞清楚 Function Calling 的消息格式。
并发执行
parallel_tools.py
当 LLM 一次返回多个 tool_calls 时，用 asyncio.gather() 并发执行，避免串行等待。 比如「同时查北京和上海的天气」会触发两次工具调用。
错误处理
error_handling.py
三类错误场景：参数校验失败（传了非法参数）、 执行异常（工具内部报错）、超时（工具超时）。 出错时把错误信息返回给 LLM，LLM 会自动调整参数重试。

Function Calling 四轮对话消息格式

# ── Round 1：用户问题 → LLM 返回 tool_calls ──────────────
messages = [
  {"role": "system", "content": "你是有工具可用的助手"},
  {"role": "user",   "content": "圆半径5，面积和周长各是多少？"}
]
# LLM 返回（不是文字，是工具调用请求）：
# role: assistant, tool_calls: [{name: "calculator", args: "{'expression':'pi*5**2'}"}]

# ── Round 2：追加工具调用请求 + 工具结果 ─────────────────
messages.append({"role": "assistant", "tool_calls": [...]})  # 加入LLM的请求
messages.append({"role": "tool", "tool_call_id": "call_xxx", "content": "78.53975"})

# ── Round 3：继续发给 LLM（此时它知道面积了，继续算周长）──
# LLM 可能再次请求调工具：calculator(2*pi*5)

# ── Round 4：LLM 拿到所有数据，给出最终文字答案 ──────────
# role: assistant, content: "半径5的圆：面积≈78.54，周长≈31.42"
关键规则：只要 LLM 的回复里有 tool_calls 字段， 你就必须把工具结果以 role: "tool" 的消息追加进历史，否则 API 会报错。 每个 tool_call 有唯一的 tool_call_id，工具结果消息里要带上它做对应。

04_rag — 检索增强生成（RAG）全链路

文本切块 → 向量化 → 存储 → 检索 → 精排 → 生成 完整流水线
为什么需要 RAG？ LLM 的训练数据有截止日期，也不知道你的私有文档。RAG 让 LLM 先从外部知识库检索相关内容， 再基于检索到的上下文回答，解决「幻觉」和「不知道」的问题。

RAG 完整流水线图

文件清单

文本切块
chunker.py
5种切块策略，返回 Chunk(text, index, start_char) 列表：
fixed_size_chunk·固定字符数+重叠，通用基础
sentence_chunk·按句子合并，适合普通文章
paragraph_chunk·按空行分段，适合报告/文档
markdown_chunk·按标题切，适合技术文档
parent_child_chunk·父块+子块两级，精准且保留上下文
向量化
embedder.py
封装本地 BGE-small-zh-v1.5 模型，不需要调用任何 API。 首次运行自动从 HuggingFace 下载（~100MB），之后本地缓存。 embed(text) 单条，embed_batch(texts) 批量，返回 L2 归一化后的 512 维向量。 归一化后两向量的点积 = 余弦相似度。
向量库
vector_store.py
Chroma 向量库封装，持久化到 data/chroma/ 目录。 add_documents(texts, metadatas) 自动 Embed + 存储； search(query, top_k) 返回带相似度分数的结果列表。 内部用 HNSW 索引，近似最近邻搜索，大规模数据也很快。
三路检索
retriever.py
BM25Retriever：按字符分词 + BM25 打分，对精确词汇匹配敏感
HybridRetriever：Dense + BM25 双路 + RRF 合并。 reciprocal_rank_fusion() 公式：每个结果得分 = Σ 1/(k+rank)，k=60 经验值， 避免任何单一结果完全主导排名。
精排
reranker.py
Cross-Encoder 模型把「查询+文档」拼在一起输入，比双编码器更精准（但更慢）。 典型用法：先用 Hybrid 召回 top-20，再用 Reranker 精排到 top-5 给 LLM。 rerank(query, docs, top_k) 返回重新排序后的结果。
端到端
rag_pipeline.py
串联所有组件的完整流水线： build_index(docs) 建库，answer_with_rag(query) 查询+生成。 Prompt 模板把检索内容注入：「根据以下内容回答：[检索结果]，问题：[用户问题]」

RRF 公式解释

RRF（Reciprocal Rank Fusion）：设两路结果各给某文档的排名分别是 r₁ 和 r₂，
该文档的融合得分 = 1/(60+r₁) + 1/(60+r₂)
→ 同时出现在两路中的文档得分更高；排名越靠前得分越高；k=60 防止最高排名结果完全压制其他结果。

05_memory — 记忆管理

短期（滑动窗口+摘要压缩）+ 长期（SQLite 持久化）
核心问题：LLM 的 Context Window 有 token 上限（通常 4k–128k）， 多轮对话如果把所有历史都塞进去，很快就超限或变慢变贵。 需要策略性地管理「什么保留、什么压缩、什么持久化」。

两种记忆的对比

维度短期记忆 short_term.py长期记忆 long_term.py
存活时间进程内，程序结束即消失写入 SQLite，永久保存
存储介质Python 列表（内存）磁盘文件 data/memory.db
容量限制受 token 窗口限制磁盘空间，无实质限制
典型内容当前对话的上下文用户偏好、反思记录、归档摘要
更新频率每轮对话都更新有意义事件时才写入

短期记忆：两种策略

策略 1
SlidingWindowMemory
只保留最近 max_turns 轮对话，超出的直接丢弃。
优点：实现简单，token 数恒定可控
缺点：早期重要信息会丢失（比如第1轮说的名字，第20轮就忘了）
token_estimate 属性粗略估算当前消耗的 token 数
策略 2
SummaryMemory
当历史对话超过 summary_trigger 轮时，把早期部分发给 LLM 压缩成摘要， 摘要注入 System Prompt，最近 recent_turns 轮保留原文。
优点：信息不完全丢失，还能保持合理的 token 数
缺点：多一次 LLM 调用，摘要有信息损失

长期记忆：SQLite 表结构

-- data/memory.db 表结构

    id        INTEGER PRIMARY KEY AUTOINCREMENT,

06_multi_agent — 多 Agent 协作系统

专业化分工 · Pipeline 串行 · 共享黑板两种协作模式
为什么要多 Agent？
单 Agent 的局限：① Token 窗口有限，处理大任务会超限；② 让一个 Agent 又搜索又写作， 工具太多容易「乱用」；③ 复杂任务难以并发。
多 Agent 解法：专业化分工——每个 Agent 只有特定工具，只做自己擅长的事， 结果通过「传参」或「共享黑板」交换。

两种协作模式对比

模式数据流向实现方式适合场景
Pipeline 串行 A → B → C 依次传递 result = agent_B.run(task, context=result_A) 步骤有明确先后顺序
共享黑板 每个 Agent 写入字典，协调者读取汇总 Blackboard.write()/read() 多 Agent 并行调研，最后汇总

多 Agent 协作图

文件清单

基类
base_agent.py
定义 Agent 三要素：name（日志标识）、system（System Prompt + 职责）、 tools（工具 Schema 列表）。
BaseAgent.run(task, context) 实现通用的 ReAct 循环， 子类只需传入不同的 system 和 tools，即可创建行为完全不同的 Agent。
context 参数：其他 Agent 传来的背景信息，追加到 System Prompt 末尾。
专业化
search_agent.py
create_search_agent() 工厂函数，返回一个只有 web_search 和 query_knowledge_base 两个工具的 Agent。 System Prompt 要求它「整理成结构化的关键事实列表」，不做写作工作。 工具隔离意味着它不可能去做其他 Agent 的事情。
专业化
writing_agent.py
create_writing_agent() 返回只有 generate_outline 和 check_completeness 工具的写作专家 Agent。 它不能搜索，只能基于已有信息写作——这就是多 Agent 系统「专业化」的本质。
协调者
orchestrator.py
提供两种协作模式：
pipeline_run(topic)：搜索→写作串行传递
blackboard_run(topic)：多 Agent 并行写入 Blackboard 共享字典， 协调者最后调用 to_context_string() 把所有发现汇总成文字，注入写作 Agent。

如何「让 Agent 知道」其他 Agent 的发现

# 方式1：直接传 context（Pipeline 模式）
search_result = search_agent.run("搜索 XXX")
article = writing_agent.run("写文章", context=search_result)  # ← 直接字符串传递

# 方式2：黑板模式
board = Blackboard()
board.write("搜索Agent-A", "核心概念", result_a)
board.write("搜索Agent-B", "实际应用", result_b)

context_str = board.to_context_string()   # 转成文字摘要
final = writing_agent.run("综合汇总", context=context_str)  # 注入写作 Agent

设计决策与扩展思路

为什么这样设计 · 如何继续扩展

关键设计决策

决策选择理由
Embedding 模型 本地 BGE-small-zh-v1.5 不依赖 OpenAI API，不产生额外费用，离线可用，中文效果好
向量库 ChromaDB（本地） 开箱即用，数据持久化到磁盘，适合单机学习场景；生产可换 Milvus/Weaviate
LLM 接入方式 OpenAI 兼容接口统一封装 一套代码适配 DeepSeek / Qwen / 任何国产模型，只需改 config.py
工具系统 Mock 实现 + 真实 Function Calling 格式 不依赖网络/外部 API，能跑通完整流程；格式与生产完全一致，可直接替换真实工具
记忆系统 SQLite（不用向量库） 记忆查询按类别/时间过滤即可，不需要语义搜索；SQLite 零配置，随代码库携带
多 Agent 通信 context 字符串 + Blackboard 最简实现，信息用自然语言传递。真实场景可以加向量检索或 structured JSON 协议

RAG 增强

记忆升级
把 long_term.py 的 SQLite 全文检索升级为向量检索：
在 save() 时同时用 embedder 计算向量存入向量库， load() 时用语义相似度而非类别过滤检索—— 这就是「自动记忆」的雏形
并发 Agent

Agent-A 和 Agent-B 同时执行，结果都写入 Blackboard， 减少总等待时间——适合多个独立子任务的场景
